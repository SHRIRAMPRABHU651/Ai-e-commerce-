# Marketing, tracking and growth

Owner: events workstream. Admin page: `/admin/campaigns` (permissions `marketing:read` / `marketing:write`).

**Status legend.** Implemented = code + unit tests. Unverified = implemented against vendors' public documentation, never run against a live account. Planned = not built.

## 1. Server-side conversion events (implemented; adapters unverified)

Pipeline: generator or browser -> canonical event (hashed identifiers only) -> `events_outbox` row per (eventId, provider) -> `events_deliver` job (every minute) -> adapter.

- Canonical events: `page_view, view_item, search, add_to_cart, begin_checkout, purchase, refund, return, repeat_purchase, referral, signup, loyalty_earn, loyalty_redeem, loyalty_tier_up`. Loyalty/creator code emits via `emitMarketingEvent(ctx, {...})`; nothing generates loyalty events by itself yet.
- Generators (`events_generate`, every 5 min, cursor `events_cursors` with a 10-minute overlap; idempotent through the unique `(eventId, provider)` index): `purchase` + `repeat_purchase` from paid non-demo orders (value = subtotal minus discount, no shipping/tax), `refund` from succeeded refunds, `return`, `signup`, `referral`. First run looks back 24h only. `orders.ts` is not touched.
- Outbox: retry with exponential backoff (30s doubling, cap 6h, +-25% jitter), 8 attempts, then `dead` (kept until an admin retries; sent/suppressed/skipped rows expire after 90 days). Events older than a platform accepts (GA4 72h, Meta/TikTok 7d) are `skipped`. In `log` mode rows end as `skipped: log_mode_not_delivered`, never `sent`.
- Admin: integration health (configured / missing credentials / mode / outbox depth / dead letters / last success) with retry buttons, and a redacted event stream inspector (hashes truncated).

### Dedupe design
`eventId` is the shared key. Server money events use `<name>:<businessKey>` (`purchase:<orderId>`, `refund:<refundId>`), so the browser `PurchasePixel` and the server job produce the same id without talking to each other. Browser funnel events generate `<name>:<uuid>` once, pass it to the pixel (`eventID` / `event_id`) and to `POST /events/track`. Meta/TikTok dedupe on event name + id. GA4 has no event-id dedupe: purchases dedupe on `transaction_id` (= order id). Google Ads dedupes on `orderId`.

### Adapters (all: implemented against public docs, unverified against live accounts)

|---|---|---|---|

| GA4 Measurement Protocol | `POST google-analytics.com/mp/collect` | `GA4_MEASUREMENT_ID`, `GA4_API_SECRET` | Needs the browser `_ga` client id (captured with consent); otherwise a synthetic `server.*` client id is used and the hit will not join a web session. | Google Ads conversion upload | `uploadClickConversions` (purchase, keyed by gclid/gbraid/wbraid and/or hashed email, `orderId` dedupe) and `uploadConversionAdjustments` (refund -> RETRACTION or RESTATEMENT) | existing `GOOGLE_ADS_*` OAuth set + `GOOGLE_ADS_PURCHASE_CONVERSION_ACTION_ID`, optional `GOOGLE_ADS_LOGIN_CUSTOMER_ID`, `GOOGLE_ADS_API_VERSION` (check the current supported version) | Whether the account needs click conversions, enhanced conversions for web (adjustments) or leads must be confirmed in Google Ads. |

Config: `EVENTS_PROVIDERS` (csv) enables providers; `EVENTS_MODE=log|live`. Production refuses start-up if any provider is enabled while `EVENTS_MODE=log` or credentials are missing (`eventsConfigProblems`). With no provider enabled nothing is queued.

### PII hashing
SHA-256 of normalised values: email trimmed+lowercased (Google flavour also strips gmail/googlemail dots); phone to E.164 (US/CA/IN default country codes; never guessed otherwise) - Meta hashes digits without `+`, TikTok/GA4/Google Ads hash with `+`. Raw email/phone are never stored in the outbox, logs or admin views. Unit tests use fixed vectors.

### Consent behaviour
Default is no consent. `hasTrackingConsent`: explicit session choice from the banner wins (an explicit "no" beats everything); otherwise a checkout marketing opt-in on the cart or `Customer.marketingConsent` counts as a grant. Meta/TikTok/Google Ads need marketing consent; GA4 needs analytics or marketing consent. Without consent the event is stored **redacted** as `suppressed` (volume visible, no identifiers) and never sent. Consent withdrawn after queuing stops delivery (checked at send time via the session). Attribution (`/events/attribution`) stores nothing unless the session has a recorded consent. The email path additionally uses customer360's `canContactUser` (see section 3).

## 2. Browser pixels and consent banner (implemented)
`apps/web/src/components/tracking.tsx`, mounted in the store layout. `getConsentState()` reads the first-party `orvia_consent` cookie. Meta Pixel, GA4 gtag and TikTok Pixel load only after consent (IDs from `NEXT_PUBLIC_META_PIXEL_ID`, `NEXT_PUBLIC_GA4_MEASUREMENT_ID`, `NEXT_PUBLIC_TIKTOK_PIXEL_ID`); the banner shows only when a choice is missing. UTM and click ids (fbclid, gclid, ttclid, gbraid, wbraid) plus `_fbp/_fbc/_ttp/_ga` are posted to the API only after consent and stored on `events_sessions` (first and last touch). Order -> session join: `Cart.convertedOrderId` -> cart token -> session.
Integration for other code: fire `trackEvent({name:'add_to_cart', productId, value, currency})` (or dispatch `orvia:track`), place `<PurchasePixel orderId value currency />` on the order confirmation page, add a footer link calling `reopenConsent()`. Product ids sent to pixels are the product `id`, identical to the feed `id`.

## 3. Segments and email campaigns (implemented)
Segments: AND-rules over real data: order count, days since last order, lifetime value (USD, converted from paid orders - not `Customer.lifetimeValue`, which sums mixed currencies), country, marketing consent, category affinity. Counted on demand (scan capped at 20,000 customers, flagged when truncated). Customers who never ordered never match recency rules.
Campaigns: draft -> test send (to your own account email only, `[TEST]` prefix) -> send now or schedule (`events_campaign_dispatch`) -> per-recipient jobs through `notify`. Recipients must have marketing consent, not be on `events_unsubscribes`, not have been emailed in the last 3 days, and fit the campaign cap and the daily cap `EVENTS_EMAIL_DAILY_LIMIT`. Consent and suppression are re-checked immediately before each message; account holders must also pass customer360 `canContactUser(email,'promotions','email')`. Signed unsubscribe link (HMAC, no expiry) in every footer; `GET`/`POST /api/v1/unsubscribe` records the opt-out, sets `Customer.marketingConsent=false`, clears cart consent (stops abandoned-cart mail) and audits. Clicks use signed `/api/v1/r` redirects restricted to the store origin. Opens are deliberately not tracked. Results show sent vs dev-logged (not delivered) vs failed. Abandoned-cart stats appear in the Attribution tab. Not done: `List-Unsubscribe` header (the notification layer has no header support).

## 4. Experiments (implemented)
Definitions in `events_experiments`; deterministic bucketing = SHA-256(`key:visitorId`) mapped onto weights; `useExperiment(key)` hook; exposure and conversion are recorded server-side (one each per visitor; client cannot choose a variant; conversions need a prior exposure). Visitor id = the per-session id (no persistent id), so returning visitors in a new session may be re-bucketed. Results: pooled two-proportion z-test, 95% CI, Bonferroni-adjusted alpha, "not enough data" below 200 visitors per variant or 30 total conversions, plain-language summary. Nothing is auto-shipped.

## 5. Attribution and performance (implemented)
Channels from stored touches (paid google/meta/tiktok by click id or utm, email, creator, organic search/social, referral, direct, unattributed). Last- and first-touch views. Per channel: orders, net sales (after refunds), contribution (ledger contribution minus refunds; orders without supplier cost are excluded), ad spend (`AdMetric`, non-demo), CAC, retained contribution, and guidance by retained contribution only; fewer than 30 attributed orders = "insufficient data". Existing `MeasuredCpa` store rows are shown read-only. Attribution coverage is displayed; unconsented orders are "unattributed", so CAC is an upper bound. Product table: views -> carts -> orders -> net sales/contribution (refund-proportional).
**Paid activation stays proposal-only.** Verified in code: `launchCampaign` enforces per-campaign, daily and monthly caps, compliance, stock; `ad_optimization` defaults to ASSISTED. The `launch_campaign` proposal now passes `requireHuman: true` (fixed at merge), so a test-campaign launch always needs a human even if `ad_optimization` is AUTOMATIC. This workstream adds no code path that spends money.

## 6. Feeds and SEO (implemented)
Feeds: Google Merchant RSS and Meta CSV per country at `/feeds/google/{US|CA|IN}.xml` and `/feeds/meta/{..}.csv` (proxied from the API). Listed: sellable state, compliance passed, not demo, `imageStatus=READY` with a non-placeholder image, valid positive price in an enabled market. Availability mirrors stock. Compare-at prices are never emitted (no verified price history). XML and CSV escaped (CSV formula-injection guarded). Not listed: shipping rules/GTIN (set `identifier_exists=no`; configure shipping in Merchant Center).
JSON-LD: pure `buildProductJsonLd` / `buildBreadcrumbJsonLd` / `serializeJsonLd` in `apps/web/src/lib/structured-data.ts` and the `ProductStructuredData` component; Offer omitted without a valid price; `aggregateRating` only when `rating.count > 0`. Sitemap: home, categories, need pages, products (paginated up to 2,000), help/track/legal. Robots: private areas disallowed, feeds allowed. **Canonical/hreflang:** the storefront serves every country from one URL (country from cookie/geo), so there are no per-country alternates and no hreflang; feed `link`s use the single URL, so Merchant Center sees geo-dependent prices - a URL-level country override would be needed for strict per-country feed matching.
