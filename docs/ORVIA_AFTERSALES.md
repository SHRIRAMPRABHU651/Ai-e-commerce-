# ORVIA after-sales

ORVIA owns the customer relationship after the sale; suppliers fulfil. This document covers returns, exchanges, refunds, chargebacks, supplier recovery and payment hardening. Rule that runs through all of it: **deterministic code decides money, eligibility and state; staff authorize; nothing promises a return the supplier cannot support.** Legend: **Implemented** (tested with in-repo mocks), **Needs live credentials** (written against public provider docs, never run against a real account), **Planned**.

Code: `packages/core/src/domain/aftersales/*` (pure rules in `policy|eligibility|refundMath|stateMachines|evidence|chargebackRules|webhookRules|refundTimeline|labels.ts`; services in `service|claims|chargebacks|paymentOps|webhookClaim|refundEvents.ts`), models `packages/database/src/models.aftersales.ts`, routes `apps/api/src/routes/aftersales.ts`, UI `apps/web/src/components/aftersales*.tsx`. The original one-step `/returns` flow and `decideReturn` are unchanged and still work.

## Returns (implemented)
- **Data model.** The core `Return` document stays the coarse record. `aftersales_returns` extends it 1:1 (RMA number, state, items with quantity/condition, evidence, eligibility snapshot, instructions, label, inspection, refund calculation, notes, timeline).
- **Eligibility engine** (pure). Inputs: payment status, delivery date, country window, reason, item condition, product category, quantities already returned (new RMAs and legacy returns), supplier policy, open returns. Output per line: eligible or a list of `{code, message}` reasons shown to the customer, `maxQuantity`, allowed resolutions, return method (`ship_back` / `staff_decides` / `none_needed`), `needsStaffReview`.
  - Seller-fault reasons (damaged, defective, wrong item, missing parts, not as described, never arrived) use the country window and override category exclusions and `defectOnly`.
  - Preference reasons (changed mind, size, better price) use the *shorter* of the country and supplier window, are blocked by category exclusions, `supportsReturns = no`, `defectOnly`, and used/damaged condition.
  - **Supplier policy unknown** (the default): the customer can *request*, the line is flagged for staff review, and no replacement/exchange is offered. Replacement requires `supportsReplacement` and a seller-fault reason; exchange requires `supportsExchange`.
  - The server re-validates the customer's selection (`validateSelection`) at submission; the wizard is advisory.
- **Reason taxonomy** (`RETURN_REASONS`): 10 codes with fault side, group and evidence requirement (`required` / `recommended` / `none`).
- **Evidence.** JPEG/PNG/WebP only, magic-byte sniffed (declared MIME must match), min 1 KB, max `MEDIA_MAX_BYTES`, max 6 per return, owner (or staff) only, only while the RMA is submitted/authorized/in transit. Images are decoded and re-encoded to WebP (max 2000 px, EXIF/GPS stripped) and stored under `aftersales/evidence/<returnId>/<uuid>.webp` through the existing storage port. Evidence is **not** served from the public media route: it is streamed through an ownership/permission-checked endpoint (`Cache-Control: private, no-store`). A reason with `required` evidence blocks RMA authorization until a photo exists.
- **RMA workflow** (`RMA_MACHINE`): `submitted → authorized → in_transit → received → inspected → refund_pending | replacement_pending → resolved`, with `rejected`/`cancelled` exits. Illegal transitions return 409. Authorization, rejection, receipt, inspection, refund, replacement, label and notes are staff actions (`returns:write`; refunds need `refunds:write`), each audited. Core `Return.status` is kept in step (`approved`, `received`, `refunded`, `rejected`). Completed replacements/exchanges set the core status to `resolved`; this value is not in the `Return` schema enum (we do not edit `models.ts`) and is written with `updateOne`, which does not validate enums. **Lead: add `'resolved'` to the enum in `models.ts` when convenient.**
- **Supplier instructions** are stored per supplier in `aftersales_supplier_policies` (accepts returns yes/no/unknown, windows, defect-only, replacement/exchange support, instructions, return address, claim window, label provider) and edited in the admin "Supplier policies" tab. Customer instructions are generated only from data we hold.
- **Labels.** `ReturnLabelProvider` interface; **no carrier integration ships**, so by default customers get written instructions. A label URL is stored only when a registered provider returned one (`source: provider`) or staff record one the supplier supplied (`source: supplier_provided`, https only). Real carrier label APIs: planned (need carrier credentials).
- **Replacement / exchange.** Allowed only when the supplier policy supports it. Exchange is limited to variants of the same product at an equal or lower price (a higher price is refused: place a new order); a price difference in the customer's favour is refunded through the guarded refund path. ORVIA does not place the replacement supplier order automatically: staff place it with the supplier and record the reference/tracking (`replacement-shipment`), and delivery resolves the RMA. Planned: automatic replacement supplier orders.
- **Refund math** (`computeRefund`, pure integer minor units; USD/CAD/INR all exponent 2). Discount, tax and shipping are allocated by *cumulative proportion of goods value*, so returning every unit across several requests refunds exactly the order total (no drift; verified in unit tests). Shipping refund rule per country (`fault_only` default for US/CA/IN, or `full_return`, `always`); tax-inclusive countries (IN) add no separate tax; optional restocking fee (bps) and return-shipping deduction apply only to customer-fault reasons and default to 0; result is capped at what remains refundable. These policy values are **business defaults, not legal advice**; edit via `PUT /admin/aftersales/policy` (`settings:write`). A staff goodwill override can lower but never exceed the computed amount.
- **Refund execution** goes through the existing guarded `refundOrder` (idempotency key `ret-<returnId>`, approval limit for non-admin staff, audit). A `pending_approval` refund leaves the RMA in `refund_pending`; approving it via the existing `/admin/refunds/:id/approve` completes the RMA through the `aftersales_refund_sync` job (every 15 min) or on the next sync.
- **Customer refund tracking.** `buildRefundTimeline` is built only from the real `Return`, `Refund` and `Payment` records; it makes no claims about bank timing beyond "depends on your bank or card issuer". `GET /aftersales/orders/:orderNumber/status` feeds `<AftersalesOrderStatus>`.
- **Supplier recovery claims** (`aftersales_claims`): kinds defect / non_delivery / wrong_item / damaged_in_transit; states `draft → submitted → acknowledged → accepted | partially_accepted | rejected → recovered | written_off` (rejected may be resubmitted). Claimed amount is capped at what was paid to that supplier for the order (from `Shipment.cost`); approved ≤ claimed, recovered ≤ approved; deadline from the supplier's claim window or the platform default (30 days). Recovered amounts are stored for the finance workstream; nothing is posted to a ledger here.
- **Disputes / notes.** Internal or customer-visible notes per RMA, full timeline, audit log entries for every action.
- **Analytics** (`GET /admin/aftersales/analytics`): returns by reason and resolution, by country (returns ÷ orders), by product (returned ÷ sold units) and by supplier (returned ÷ shipped units), from real data. Rates with a denominator below 20 are returned as `null` and shown as "insufficient data". Returns created before the RMA flow have no reason detail and are counted separately.

## Chargebacks / disputes
- **Ingestion (implemented with mocks; Stripe/Razorpay need live verification).** Stripe `charge.dispute.created|updated|closed|funds_withdrawn|funds_reinstated` and Razorpay `payment.dispute.*` are parsed by the adapters *after signature verification* into a provider-neutral `ProviderDispute`, then stored in `aftersales_chargebacks`, unique on (provider, disputeId). Replays and out-of-order events only update state through `nextChargebackState` (a terminal state is never reopened; a provider "needs_response" replay does not undo recorded/submitted evidence). If a dispute carries only a charge/payment id, the adapter's `resolveIntentFromCharge` finds the payment; a dispute that cannot be matched is stored with `unmatched: true` for manual matching.
- **Evidence deadline tracking**: `deadlineState` (ok / due_soon within 72 h / overdue); the hourly `aftersales_chargeback_deadlines` job raises deduplicated critical `CHARGEBACK` exceptions. Dispute exceptions deliberately carry no `orderId`, because raising an exception with an order flips the order to `EXCEPTION`.
- **State machine**: `warning → needs_response → evidence_recorded → submitted → under_review → won | lost`, plus `accepted` and `closed`.
- **Admin workflow** (permission `refunds:approve` to write, `payments:read` to read): record evidence (text + category), "Send to provider", accept loss. Recording is always local. **Sending to the provider API is implemented behind the adapter but UNVERIFIED** (Stripe `disputes.update` with text fields only; Razorpay `PATCH /disputes/:id/contest` with summary only). File evidence (receipts, proof-of-delivery documents) is not uploaded. The result is stored as `submitted_unverified`; always confirm in the provider dashboard before the deadline.
- **Finance hooks**: `chargebackReserve` / `sumReserves` (pure) and `chargebackReserveSummary()` / `GET /admin/aftersales/chargebacks/reserve` expose held / lost / released / fee per currency from stored amounts. Convention: open disputes hold amount + fee; won releases the amount (fee lost); lost/accepted is a loss of amount + fee; warnings (inquiries) hold nothing. The finance workstream decides how to post this.
- **Chargeback rate**: disputes ÷ successful payments in the window, per currency and overall, flagged `reliable: false` ("insufficient data") under 100 transactions; an attention flag at 0.75 % is a prompt to investigate, not a statement of any card-network threshold.
- **Mock provider** supports `simulateDispute` (signed webhook through the real verification path). Route `POST /dev/aftersales/simulate-dispute` exists only outside production/staging with `PAYMENT_MODE=mock` and requires staff.

## Payments hardening
- **Webhook idempotency.** Existing: signature verification on the raw body, event-id dedupe with a unique index, re-fetch from the provider before marking paid, atomic order update. **Gap found and fixed:** the event id was claimed *before* processing, so a crash mid-processing turned the provider's retry into a permanent "duplicate" (a lost payment confirmation until the 5-minute poll). Claims now finish by writing an `outcome`; an unfinished claim older than 2 minutes is atomically reclaimed on retry (`claimWebhookEvent`, `decideWebhookDedupe`). All handlers are themselves idempotent, so reprocessing is safe. The hunk in `orders.ts` is small and localized.
- **Authorize vs capture.** `CreatePaymentInput.captureMode` (`automatic` default = unchanged behaviour). Stripe: `capture_method: manual`, `capture`, `cancelAuthorization`, `requires_capture → authorized`, `payment_intent.amount_capturable_updated → payment.authorized`. Razorpay: `authorized` status read from the payments list and `POST /payments/:id/capture` (whether payments are auto-captured is a Razorpay account setting). `capturePayment` verifies with the provider, captures with an idempotency key, then settles through the same `settlePayment` as a webhook. **Checkout does not use manual capture**; it is infrastructure for staff-triggered capture (`POST /admin/aftersales/payments/:id/capture`, `refunds:approve`).
- **Refunds.** Existing flow is idempotent; Stripe `charge.refund.updated`/`refund.updated` with status failed now becomes a `refund.failed` event: the refund is marked failed and a critical exception is raised (order/payment totals are not auto-reversed because a human must reconcile the money).
- **Failed payments.** Existing `payment.failed` handling kept. New `reconcileWithProvider` (job every 6 h, read-only provider calls, `POST /admin/aftersales/payments/reconcile`): settles payments the provider reports succeeded but we hold pending, marks payments the provider reports failed as failed, and raises deduplicated `RECONCILIATION` exceptions for the rest (`comparePaymentState`). The existing ledger reconciliation (`reconciliation.ts`) is untouched.

## Endpoints (all under `/api/v1`)
Customer (signed in, ownership enforced): `GET /aftersales/reasons`, `GET /aftersales/orders/:n/eligibility?reason=`, `GET /aftersales/orders/:n/status`, `POST /aftersales/returns`, `GET /aftersales/returns[/:id]`, `POST /aftersales/returns/:id/evidence`, `GET /aftersales/returns/:id/evidence/:eid`.
Staff: `GET|POST /admin/aftersales/returns[...]` (authorize, reject, received, inspect, refund, replacement, replacement-shipment, label, notes, evidence), `GET|PUT /admin/aftersales/suppliers/:id/policy`, `GET|PUT /admin/aftersales/policy`, `GET|POST /admin/aftersales/claims[/:id/transition]`, `GET /admin/aftersales/analytics`, chargebacks (`GET`, `/metrics`, `/reserve`, `/:id`, `POST /:id/evidence|submit|accept`), `POST /admin/aftersales/payments/:id/capture`, `POST /admin/aftersales/payments/reconcile`.
Jobs: `aftersales_chargeback_deadlines` (1 h), `aftersales_provider_reconciliation` (6 h), `aftersales_refund_sync` (15 min).

## Known gaps (honest list)
- One open return per order (inherited from `requestReturn`); multi-supplier orders use the first item's supplier for instructions/labels/replacement checks.
- Replacement/exchange supplier orders are manual (staff record the result).
- No customer-facing exchange variant picker; the wizard collects the request and staff finalize (the API accepts `exchangeSku`).
- Dispute file evidence upload to the provider is not implemented.
- Supplier claim creation has an API but no dedicated admin form (the tab lists and transitions claims).
- Integration tests in `tests/integration/aftersales.test.ts` were written but **not executed** (no MongoDB in the authoring sandbox); unit tests in `tests/unit/aftersales.test.ts` run without a database.
