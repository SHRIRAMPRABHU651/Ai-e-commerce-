# Honest limitations

Verified in the original release: lint, typecheck, 253 unit/integration/failure/security tests (coverage floors on `packages/core`: lines ≥ 80%, branches ≥ 70%), Playwright E2E (desktop + mobile), production builds, a high-severity `npm audit` — all against in-repo mock providers. **Update (reinvention build):** only lint, typecheck, DB-less unit tests (463 passed), builds and a boot check were executed there; the Mongo-backed integration tests and Playwright were written but not executed (see [ORVIA_TEST_REPORT.md](ORVIA_TEST_REPORT.md)). Consolidated list and next steps: [ORVIA_LIMITATIONS_AND_NEXT_STEPS.md](ORVIA_LIMITATIONS_AND_NEXT_STEPS.md). Not verified:

1. **Live provider adapters** (the generic `rest` supplier adapter is tested against fake HTTP suppliers only; real suppliers' payload shapes will need mapping tweaks) (CJ, Stripe, Razorpay, Meta, TikTok, Google Ads, Resend, Twilio, Gemini) have never run against real or sandbox accounts from this repo. Expect to fix field-mapping details during staging verification.
2. **Ads**: Google creates campaign + budget only; TikTok creates campaign + ad group only (no creative upload). Meta creates the full chain paused. Pixel/CAPI/product-feed setup is manual.
3. **Market intelligence**: the crawler/trend engine is tested against a local fake site only; no real public source has been crawled from this repo. Trends reflect the sources you configure. FX is now a provider interface (`frankfurter`, `exchangerate_api`; `static` is dev/test only and refused in production) with stored rates and a staleness policy, but the HTTP adapters have never run against the live services, and a few paths (`adsService.ts`, `importer.ts`, `pricing.ts`, `market/index.ts`) still read the static table.
4. **Terraform** passes `terraform init`/`validate`/`fmt -check` on a GitHub-hosted runner (CI run https://github.com/SHRIRAMPRABHU651/Ai-e-commerce-/actions/runs/40061120584) but has **never been planned or applied** against any AWS account, so IAM, networking and cost behaviour are unverified; MongoDB Atlas networking is out of module scope.
5. **Tax & duties** are estimates (regional rate tables, simple duty model). Use a tax service for compliance.
6. **Images**: real product photos come from the live supplier API only (see SUPPLIERS.md); the mock supplier's demo data uses generated SVG art, accepted in development only. The CJ image-field mapping is unverified against a live account. Images are re-hosted into Orvia storage (production never hotlinks); S3Storage has not run against a real bucket, and the CDN is not provisioned by Terraform (`cdn_base_url` is an input).
7. **Search** is in-process (typo tolerance via fuzzy matching over an in-memory index) — fine for thousands of products; move to OpenSearch/Atlas Search at scale.
8. **Email/SMS** templates are functional but plain; deliverability setup is yours.
9. Admin tables are server-paginated but not virtualised; very large catalogs may need tuning.
10. Seed/demo data is development-only; production must start empty.
11. **Ads**: consent-gated server-side conversion events (Meta CAPI, TikTok Events API, GA4, Google Ads) and browser pixels now exist but have never run against live accounts; AI ad spend is proposal-only and launches always need a human; platform status stays UNVERIFIED until a live check passes.
12. **Named vendors still without an adapter**: AliExpress, DSers, Spocket, Zendrop, Syncee, DropCommerce, Wholesale2B, Modalyst, Printful, Printify. A read-only `feed` adapter (CSV/JSON catalogue, price, stock) and the `manual` adapter now exist alongside `rest` and `cj`; none has run against a real vendor.
13. **Live provider checks** (Stripe/Razorpay/Resend/Twilio/Gemini endpoints used by `verify:staging`) are call shapes written from documentation and unverified against real accounts.
14. **Organic claims**: certificate authenticity is attested by the admin; no certifier registry lookup.
15. **Migration**: on an existing database drop the legacy `orderId_1_lineKey_1` Shipment index before `npm run migrate`.
16. **Legal review** is an operator attestation; Orvia cannot detect it. Export and destination-market obligations are now a hard gate (see #18), but whether a supplier-direct, no-inventory model qualifies under India's inventory-based cross-border export framework is a legal question Orvia cannot answer.
17. **Acquisition cost (CPA) is ASSUMED until real campaign data exists.** No ad campaign has run from this repo, so every product resolves to `cpaSource: 'assumed'`: the expected case uses the configured `cacScenarios.expected` (26% of price), not a measurement. Such products cannot be auto-published; a person must approve. The measured-CPA store, the product → category → store resolution, and the `ESTIMATED` / `measured` labelling are tested against synthetic ad metrics and manual entries only. The 15% / 26% / 40% scenario fractions are starting assumptions, not market data. Measured CPA counts platform-reported purchases capped at real paid orders per product+country (so two platforms claiming the same customer cannot understate it), but attribution is otherwise not deduplicated per customer and organic buyers can still be counted: the blended figure can understate true acquisition cost — keep the measurement scope to one channel until a deduplicated attribution method exists. Refund rate is likewise estimated (base rate + reliability + transit time) until `minRefundSample` real orders exist per product–supplier–destination; measured refund attribution splits a multi-supplier order's value evenly across its (product, supplier) pairs.
18. **Export attestation** (`legal.exportAttestations`) records that an operator says an adviser was consulted for a destination; it does not validate the adviser, the reference, or the advice. The gate defaults ON in production only (`requireExportAttestation`), so dev/test and seed flows are unaffected. It is not overridable by `force`, exception approval, the AI executor or a supplier change (tested).
19. **Referrals** (`docs/GROWTH_STRATEGY.md`): one reward per invited email, paid only after delivery + a 14-day hold, never for the referrer's own email/account or high-fraud orders. It cannot detect alias emails (e.g. `+tag` or dotted addresses), shared households or friend rings, so treat reward cost as a marketing budget line, not a guarantee. Reward codes are single-use and unguessable but are not bound to the referrer's email: anyone who receives the code can use it once. The Mongo-backed tests for this flow (`tests/integration/growth.test.ts`) were written but could not be run in the sandbox that produced them (MongoDB binary download blocked); run `npm test` in CI before relying on them.
20. **Shop by need** collections are rule-based matches on category and keywords, not learned from behaviour. Whether shoppers actually navigate by need is untested; the principle tags on each need are hypotheses.
21. **Reinvention build (trust, rescue, after-sales, customer 360, find, finance, creators, events, supplier network, AI agents)**: pure logic is unit-tested, but every Mongo-backed integration test for these areas and every new Playwright spec was written and not executed in the build session. Live Stripe/Razorpay dispute, capture and refund-event paths, supplier cancel/reorder in Delivery Rescue, Gemini-backed features (image search, AI refinement, model wording), FX adapters, tracking adapters and email delivery are unverified. Trust scores, delivery bands and advocate metrics have never seen real transactions; thresholds are design choices, not calibrated.
22. **Not built**: carrier return labels, automatic dispute file-evidence upload, PSP payout reconciliation, automated creator payouts/KYC/tax forms, MFA, neural embeddings, price history on the passport, load-test results. Admin UI is missing for staff users, export attestation (a hard publish gate in production), manual offers/fulfilment and several settings (API only).
23. **Deployment**: Docker images were not built and Terraform was not planned/applied in the reinvention build; `deploy.yml` does not apply the new image tag to the task definitions and its migrations step only echoes. `NEXT_PUBLIC_*` pixel ids are build-time and the Dockerfile has no build args for them.
24. **See** [ORVIA_LIMITATIONS_AND_NEXT_STEPS.md](ORVIA_LIMITATIONS_AND_NEXT_STEPS.md) for the consolidated list, the per-provider credential list and the "before accepting real customer payments" checklist.
