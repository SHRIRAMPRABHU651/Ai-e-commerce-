# ORVIA customer experience (customer360 workstream)

Customer relationship layer: Customer 360 for staff, and LifeGraph, Commerce Memory, a privacy centre, a product companion and an aftercare hub for customers. Everything is built from data that exists; where a fact is missing the UI says so ("Not provided by the supplier yet").

Code map: pure logic `packages/core/src/domain/customer360/{lifegraph,consent,privacy,companion}.ts` (no IO, unit-tested), DB layer `service.ts`, models `packages/database/src/models.customer360.ts` (collections `customer360_*`), routes `apps/api/src/routes/customer360.ts`, UI `apps/web/src/components/customer360.tsx`, nav in `components/account.tsx`, admin `/admin/customer-360`.

## Customer 360 (staff)
Permissions: `customer360:read` (search, profile, deletion queue), `customer360:write` (notes, withdraw consent, process deletion, reveal contact details). Default roles: SUPPORT has read; ADMIN/SUPER_ADMIN have both; ANALYST has read (all `:read` permissions).

- `GET /admin/customer-360?q=` search by email prefix or name (min 2 chars). Results are masked (`j***@e***.com`, `Jane D.`). The query text is not audited (may be PII); its length and result count are.
- `GET /admin/customer-360/:userId` aggregates: identity, preferences, LifeGraph interests, purchase history (Customer.ordersCount / lifetimeValue as recorded), wishlist count, favourite collections, product-interaction counts (AnalyticsEvent, 90 days), support tickets, shipments, returns, refunds, loyalty (defensive read), referral code and rewards, consents + history, risk flags, staff notes, deletion requests, and a merged timeline. No addresses, phone, IP, message bodies or card data are returned.
- Every view writes audit `customer360.view`. `?reveal=email&reason=` (write permission, reason required) un-masks email/name and writes `customer360.pii_reveal`.
- Writes (all audited): `POST .../notes`, `POST .../consents/withdraw` (staff can only withdraw, never grant), `POST /admin/customer-360/deletion-requests/:id/process` (`execute | reject | hold | release`).

## LifeGraph (opt-in)
Off by default; needs the customer's switch and, to be used, `personalization` consent. Nodes are typed (`pet_type`, `eco_preference`, `budget_range`, `category_interest`, `gift_recipient`, `gift_occasion`, `child_age_band`, `style_preference`, `delivery_priority`), with `purpose`, `source` (`declared` | `derived_from_purchases`) and the consent policy version. Edges: `self -rel-> node`, and parent chains (recipient -for_occasion-> occasion).

Safety: closed allowlist of kinds and values. A deny-guard rejects sensitive kinds by name (health, religion, ethnicity, sexuality, politics, location, exact child age/birth date, income, ...) and sensitive free-text category values. Children are only a coarse band the customer picks. Purchase-derived nodes pass the same guard (e.g. repeat purchases in a health-like category are never turned into an interest), need 2+ purchases, are shown with a "From your purchases" label and are deletable. Stored nodes are re-validated on read.

`personalizationSignals(lifegraph)` (pure, exported from `@orvia/core`) returns inactive/empty signals unless enabled + consent; `personalizationSignalsFor(userId)` loads it. The only wired boost is `GET /account/recommendations`: existing `recommendedForYou` candidates are re-ranked by `rankWithSignals`, each boost carrying a "Because you told us ..." reason. Budget is relative to the candidate set, never an absolute price claim. Customers can view, add, delete one/all, run the purchase suggestion, and download JSON (`GET /account/lifegraph/export`).

## Commerce Memory
Customer-controlled items `{kind, title, payload}` (requirement, comparison, product_question, favourite_collection, note), per-item on/off, global on/off, retention (30/90/180/365 days or until deleted), view/edit/delete/export. Expired items are deleted by the `customer360_sweep` job (every 6 h). The `find` workstream writes via `saveMemoryItem(ctx, userId, {kind,title,payload}, 'find')` (exported from `@orvia/core`); it returns `{saved:false, reason}` when memory is off/full and must only be called on an explicit customer action. Memory is not used for personalization or recommendations.

## Consent and privacy centre
- Consent kinds: `marketing_email`, `personalization`, `analytics`, `data_processing`. Append-only `customer360_consents` (timestamp, versioned policy id from `POLICY_VERSIONS`, source, optional HMAC IP hash, staff actor/reason). Current state = latest record per kind; no record = not granted. `marketing_email` also syncs `Customer.marketingConsent`.
- `canContact(profile, topic, channel)` / `canContactDecision` (pure) and `canContactUser({userId|email}, topic, channel)` (DB) are the single gate for the events workstream. Transactional topics (order_updates, security, support) are always allowed by email; every other topic needs marketing consent, an explicit per-topic per-channel opt-in, and for `recommendations`/`replenishment` also personalization consent. Deleted/disabled accounts get nothing. It fails closed for unknown users. `canContactUser` only decides; wiring existing senders to it is the events workstream's job.
- Export: `GET /account/privacy/export` returns `orvia.data-export.v1` JSON (account, orders, addresses, returns, refunds, tickets, wishlist, reviews, referrals, consents, preferences, LifeGraph, memory, interactions, loyalty, staff notes, deletion requests, notifications metadata). Secrets, fraud/cost fields and IP hashes are stripped. Rate limited (5/h) and audited.
- Deletion: customer requests (`POST /account/privacy/deletion`, immediate marketing withdrawal) -> 14-day cooling-off (cancellable) -> the sweep marks it `ready` -> staff `execute` (refused before cooling-off ends, or while on legal hold) -> `anonymizeAccount`: user/customer PII replaced by `deleted-<hash>@anonymized.invalid`, password made unusable, sessions revoked; order name/address/email removed while amounts, items, currency, country, payment/refund status stay; tickets, returns, reviews and notification bodies redacted; addresses, wishlist, carts, analytics, LifeGraph, memory, preferences, staff notes and referral code deleted; consent log kept without IP hashes; audit log kept. Each step is audited.
- Pages: `/account/privacy`, `/account/preferences` (channels/topics + LifeGraph), `/account/memory`.

## Product companion and aftercare
- `/account/products` lists items from delivered orders; `/account/products/[orderItemId]` (id = `<orderId>_<line index>`; not-found and not-yours are indistinguishable). Content comes only from product fields: description/bullets, `attributes` keys for care/usage/warranty/compatibility (normalised names such as `care_instructions`, `how_to_use`, `warranty`, `compatible_with`), `compliance.safetyInfo`, and organic evidence that is `verified` and unexpired. Missing = "Not provided by the supplier yet". Related products (`similar()`) are labelled "Related", never "compatible"; "Compatible with" appears only from an explicit attribute. Warranty only from an explicit attribute.
- Replenishment: only for products tagged `consumable`/`refill`/`replenishable`; opt-in; timing only if the product has `replenish_after_days` (or equivalent), otherwise no timing claim and no reminder. Reminders must go through `canContact(..., 'replenishment', ...)`; no sender exists in this workstream.
- Support and returns entries link to `/help` (support chat) and the order page (aftersales flow).
- `/account/aftercare` aggregates open returns, in-progress refunds, unresolved tickets, delivery issues (failed/returned shipments or past the estimated date) and rescue cases.

## Implemented vs planned
Implemented: everything above, nav entries (My products, Aftercare, Preferences, Memory, Privacy plus placeholder links `/account/price-guard`, `/account/saved-searches` for the `find` workstream), unit tests, integration tests.
Partially implemented / assumptions: loyalty and rescue are read through defensive raw-collection readers (`loyalty_accounts`, `rescue_cases`; constants `LOYALTY_COLLECTION`/`RESCUE_COLLECTION` in `service.ts`, fields `tier`, `points|balance`, `status`, `kind`, `orderId`); change them if those workstreams use other names. "Saved collections" are Memory items of kind `favourite_collection` (no separate collection model exists). Lifetime value is the stored `Customer.lifetimeValue` (not recomputed, currency not normalised).
Planned / not done: sending reorder reminders and enforcing `canContactUser` inside existing senders (cart recovery still uses `Customer.marketingConsent`); bounce/complaint suppression feed (`suppressed` currently maps to a disabled account); record-level legal-hold reasons; email confirmation of deletion; automatic anonymization without staff approval; a staff UI to edit/remove notes; integration tests have not been executed in the authoring sandbox.
